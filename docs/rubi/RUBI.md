# Rubi — decisiones permanentes

Rubi es el asistente de trabajo de la Secretaría Virtual de la FFSJ. Su objetivo no es sustituir la aplicación ni responder de forma aislada sobre ella, sino ayudar al usuario a comprender el contexto, encontrar información, navegar y completar workflows seguros dentro de Secretaría.

> No queremos que la IA responda preguntas sobre Secretaría. Queremos que ayude a trabajar en Secretaría.

## Arquitectura vigente

El flujo real es:

`Usuario → Angular (panel Rubi) → Secretaría API → RubiGateway/capa determinista → provider + tools/capabilities → servicios existentes de Secretaría`

- `ffsj-secretaria` contiene el panel Angular, la conversación efímera, el contexto de pantalla y la interfaz estructurada de alta.
- `ffsj-secretaria-api` autentica, resuelve asociación, ejercicio, permisos, scopes y capabilities. `RubiGateway` decide entre resolución determinista y provider y solo permite tools registradas.
- Los servicios ordinarios de Secretaría ejecutan las reglas y la persistencia. En el alta, Rubi prepara una referencia temporal y la confirmación humana registra la solicitud administrativa mediante `AltaWorkflow`.
- El provider nunca recibe autoridad de ejecución ni acceso a servicios o bases de datos.

## Invariantes

- El backend es la fuente de verdad para identidad, asociación, ejercicio, permisos, scopes, capabilities, reglas y resultados.
- Todo endpoint de Rubi rechaza explícitamente cualquier parámetro de entrada no reconocido (body o query), nunca lo ignora en silencio; un parámetro inesperado es un error (`RUBI_UNEXPECTED_PARAMETER`), no un dato descartado. Cada endpoint nuevo debe declarar su propio allowlist cerrado de claves permitidas, igual que ya hace `/asistente/mensaje` (RUBI-22, tras encontrar y corregir una excepción en `/asistente/sugerencias`).
- El LLM no accede directamente a las bases de datos de Secretaría ni de Censo.
- La IA no genera ni ejecuta SQL, endpoints arbitrarios o rutas no registradas.
- Permisos, scope de asociación y capabilities se calculan en backend a partir de la sesión autenticada.
- La PII sensible permanece fuera del provider. Los mensajes se sanean y un alta con datos personales usa el flujo determinista y estructurado.
- No se guardan datos sensibles en history, telemetría, logs ni almacenamiento web. La conversación vive en memoria, tiene TTL y se limpia al cambiar de contexto o cerrar sesión.
- Las tools son cerradas, tipadas y se vuelven a autorizar al ejecutarse. Las capabilities (derivadas de permisos reales) son la única puerta de disponibilidad por defecto: una tool nueva y su capability están disponibles sin tocar configuración. Una lista de bloqueo de infraestructura (`RUBI_BLOCKED_TOOLS`), vacía por defecto, puede restringir puntualmente una tool concreta como kill switch extraordinario, pero nunca al revés: una lista de tools *permitidas* que haya que mantener actualizada manualmente queda descartada como patrón, precisamente porque quedar desactualizada hace desaparecer funcionalidades nuevas sin ningún error visible.
- Toda operación persistente requiere revisión y confirmación humana explícita.
- Gemini no ejecuta altas. `start_alta` solo abre el workflow local; la confirmación llama a backend sin pasar por el provider.
- Registrar un alta administrativa crea el trámite/solicitud correspondiente; no equivale a escribir directamente en Censo.
- Se reutilizan los workflows y reglas existentes de Secretaría, sin crear una vía administrativa paralela.
- Los datos dinámicos de actividades, calendario, plazos, disponibilidad y estado de inscripción se consultan siempre en los servicios reales de Secretaría mediante tools de lectura cerradas; la KB solo explica el funcionamiento y nunca es fuente de fechas o estados concretos.
- Cuando el dominio ya dispone de una frontera humana segura, Rubi la reutiliza en vez de imponer un prepare/confirm paralelo. En inscripciones, `start_inscripcion` solo selecciona y abre el formulario dinámico oficial; participantes, respuestas y adjuntos permanecen en Angular y el envío lo realiza el usuario contra el endpoint ordinario.
- Las operaciones persistentes preservan idempotencia, bloqueo y revalidación para soportar concurrencia y reintentos.
- El patrón preparar → revisar → confirmar (opaco, con TTL, vinculado a actor/asociación, con reintento idempotente) se reutiliza en cada workflow nuevo, pero el almacén concreto (tabla) no se comparte automáticamente solo por ahorrar una migración: si el dominio nuevo no encaja en el esquema de un almacén existente (por ejemplo, exige columnas que el dominio nuevo no necesita, como el ejercicio obligatorio de altas/modificaciones/bajas para un dominio que no lo requiere), se crea un almacén propio con el mismo patrón en lugar de forzar el esquema compartido o relajar sus columnas. Tampoco se hace el refactor inverso (generalizar el almacén existente a costa de tocar los workflows que ya lo usan) solo para evitar una tabla nueva.
- Cuando una operación implica archivos, estos nunca viajan al provider ni se guardan en el almacén temporal de preparación (que solo contiene metadatos: nombre, tipo, tamaño). Los ficheros permanecen en el cliente hasta que el registro ya existe (tras confirmar) y se suben entonces mediante el mecanismo de adjuntos genérico ya existente, con una llamada Angular → API directa.
- Rubi es opcional: `RUBI_ENABLED`, los flags transaccional/provider y la allowlist del piloto permiten desactivarla o limitarla.
- La operación ordinaria de Rubi (habilitarla globalmente, o el uso del provider real) se administra desde Secretaría (Configuración → RUBI), sin necesidad de tocar variables de entorno. Esa configuración administrada es siempre subordinada a los kill switches de infraestructura (`RUBI_ENABLED`, `RUBI_REAL_PROVIDER_ENABLED`, `RUBI_TRANSACTIONAL_ENABLED`): si la infraestructura deshabilita algo, ninguna configuración administrada puede reactivarlo.
- `enabled` y `authorized` son conceptos distintos y nunca se usan indistintamente. `enabled` es el estado funcional global de Rubi (infraestructura + configuración global de Secretaría). `authorized` es la autorización explícita de una asociación concreta para usar Rubi, administrada por asociación desde Secretaría. Una asociación sin fila de configuración explícita, o ante cualquier fallo al leerla, NO está autorizada (deny-by-default): autorizar es siempre un acto explícito del panel admin. En cambio, un fallo al leer el estado global (`enabled`) es fail-open y nunca bloquea un acceso ya autorizado por las capas superiores, para no depender de que una migración ya se haya ejecutado.
- La regla de acceso en modo operativo normal es `RUBI_ENABLED (infraestructura) && enabled (configuración global) && authorized (asociación)`. La allowlist del piloto (RUBI-13) no forma parte del modo normal y nunca lo restringe: solo se aplica cuando el modo piloto está activado explícitamente por infraestructura (`RUBI_PILOT_MODE_ENABLED`), añadiendo el requisito adicional de que el actor esté en la allowlist. Toda ruta protegida de Rubi (`/asistente/acceso`, conversación, alta, modificación, baja) resuelve el acceso mediante la misma función única, para que no pueda ocurrir que `/asistente/acceso` informe autorizado y un workflow deniegue después.
- Producción es intocable sin autorización explícita del usuario en el prompt vigente.

## Actor y scope: asociación y Federación/Administración (RUBI-20)

Rubi reconoce dos scopes de actor, calculados siempre en backend a partir de la sesión autenticada, nunca del texto del usuario ni de lo que proponga el provider: `association` (un actor con asociación propia, comportamiento sin cambios desde el inicio de Rubi) y `federation` (un cargo autenticado sin asociación propia: Federación/Administración). No existe una jerarquía entre ambos ni un scope que sea superconjunto del otro; cada uno tiene su propia tabla de capabilities, calculada exactamente igual que siempre a partir de ACTOR + PERMISOS + SCOPE + CONTEXTO + reglas del dominio, nunca de lo que proponga el provider.

`admin:access` y `admin:rubi` no son permisos funcionales. `admin:access` habilita pantallas administrativas de Secretaría; `admin:rubi` habilita administrar la configuración operativa de Rubi (Configuración → RUBI). Ninguno de los dos concede, por sí solo, ninguna capability de Rubi: cada capability de Federación sigue derivando de un permiso funcional real (`asociados:read`, `registro:read`, `inscripciones:read`...), igual que para asociación. Ampliar el alcance de Federación exige añadir una entrada explícita a la tabla de capabilities de Federación con su permiso real, nunca inferirlo de un permiso administrativo.

La autorización para que Federación/Administración use Rubi (`federation_authorized`, configuración global administrada) es un concepto independiente de `authorized` por asociación: Federación no es una asociación y nunca se reutiliza esa autorización con semántica falsa. Es deny-by-default como el resto de autorizaciones explícitas de Rubi.

Algunas capabilities de Federación (las que leen datos que pertenecen a una asociación concreta: actividades, calendario, comunicaciones recibidas) exigen además una asociación objetivo (`targetAssociationId`) validada contra el sistema real de asociaciones; sin objetivo validado, esas capabilities simplemente no se conceden, nunca se ejecutan con un alcance ambiguo o global. La asociación objetivo llega siempre como un dato estructurado seleccionado por el usuario (nunca interpretado de texto libre ni propuesto por el provider) y el backend valida su existencia real antes de aceptarla; una asociación objetivo inexistente o manipulada se rechaza explícitamente, nunca se ignora en silencio. Un actor de asociación no puede desplazar su propio scope mediante este ni ningún otro campo: su asociación es siempre la suya.

Las tools que ya existían (lectura de actividades/calendario/comunicaciones) no se duplican para Federación: la misma tool sirve a ambos scopes porque ya recalculan sus datos a partir del `associationId` resuelto en el contexto de cada petición, nunca de un referente guardado de una conversación anterior. Esto garantiza que cambiar de asociación objetivo (A → B) nunca arrastra datos de A: cada petición vuelve a resolver su propio contexto desde cero. Cambiar de asociación objetivo en el panel limpia además la conversación completa en el cliente.

Los workflows transaccionales de personas y Registro (alta, modificación, baja, documentación, comunicación) quedan fuera del alcance de Federación en RUBI-20: no se ha auditado que ejecutarlos en nombre de otra asociación sea seguro con el diseño actual de sus almacenes de confirmación (ligados a actor+asociación). Ampliarlo es una decisión explícita futura, no un descuido ni un `TODO` implícito.

**Decisión permanente (corregida en 1.8.1#RUBI): el frontend nunca infiere el scope por su cuenta; consume el scope resuelto por backend.** Durante la validación manual de RUBI-20 en DEV se descubrió que el panel Rubi (`rubi-panel.component.ts`) calculaba `isFederationActor` de forma independiente como `!AuthService.getIdAsociacion()`, sin usar el scope ya resuelto por `RubiContext`/`RubiPilotAccess`. Esa función devuelve `-1` (no `0`) para un actor sin asociación propia, y en JavaScript `!(-1)` es `false`: el selector de asociación objetivo no se mostraba nunca a un actor Federación/Administración real, aunque el backend clasificara correctamente su scope. `GET /asistente/acceso` se amplió para devolver `scope` y `canSelectTargetAssociation` (nunca la asociación objetivo, PII, token ni cargos completos), y el frontend consume ese campo en lugar de reimplementar la clasificación. Cualquier decisión de UI que dependa de si un actor es Federación/Administración debe resolverse siempre así, nunca con una heurística nueva sobre el token en el cliente.

## Proactividad contextual (RUBI-21)

Rubi puede ser proactiva: puede mostrar, sin que el usuario pregunte, algo relevante que ya existe como dato real y autorizado en Secretaría (una comunicación nueva, un plazo de inscripción próximo, una solicitud pendiente). Esa proactividad tiene límites permanentes:

- **Contextual, no autónoma**: una sugerencia solo informa o propone navegar/abrir el paso siguiente ya existente (comunicaciones, soporte, una actividad, el calendario, una inscripción). Ninguna sugerencia ejecuta, confirma, crea, modifica, inscribe ni cierra nada por sí sola; toda acción sigue exigiendo al usuario entrar en el workflow real y confirmar humanamente, igual que el resto de Rubi.
- **Determinista, no decidida por el provider**: las sugerencias se calculan siempre en backend a partir de reglas fijas sobre datos reales (`RubiInsightsService`), nunca las decide, prioriza ni inventa Gemini. El provider, si interviene en la conversación, solo puede referirse a una sugerencia que el backend ya ha calculado y estructurado; no puede afirmar que existe un aviso que el contexto estructurado no le ha entregado.
- **Reglas de prioridad fijas**: `acción requerida > plazo próximo > novedad > informativo`. No hay puntuación opaca ni urgencia inventada; el orden es siempre el mismo criterio determinista.
- **Plazos con ventana fija**: una fecha límite solo se convierte en sugerencia dentro de una ventana determinista corta (no cualquier actividad futura es una alerta).
- **Reutiliza fuentes ya existentes, no las duplica**: las sugerencias de comunicaciones y actividades reutilizan exactamente las mismas tools de lectura ya auditadas y validadas (`get_comunicaciones`, `get_calendario`), nunca una consulta SQL paralela que pudiera divergir de lo que el chat ya responde. La campana (`.tasks-bell`) y la proactividad de Rubi pueden coexistir informando de lo mismo desde ángulos distintos (la campana: "esto ha pasado"; Rubi: "esto es relevante y te puedo ayudar con el siguiente paso"); no se crean dos sistemas de verdad.
- **Subordinada a permisos y scope**: cada dominio de sugerencia exige la misma capability/permiso real que ya exige su tool de lectura o su workflow equivalente; ninguna capability universal (`rubi.proactive`) puede saltarse esa comprobación por dominio. En scope Federación sin asociación objetivo validada no se genera ninguna sugerencia que pertenezca a una asociación concreta; con objetivo, solo las de esa asociación, y cambiar de objetivo recalcula todo desde cero sin arrastrar sugerencias de la asociación anterior (mismo aislamiento A/B que el resto de RUBI-20).
- **Minimización de datos**: una sugerencia expone como máximo `{id, dominio, prioridad, contador, fecha límite, título allowlisted, acción}`; nunca texto libre de base de datos, el cuerpo de una comunicación, la descripción de un ticket ni una entidad completa.
- **Sin persistencia nueva salvo necesidad real**: las sugerencias se calculan bajo demanda a partir de los servicios reales existentes; no se ha creado una tabla de "notificaciones Rubi" ni un estado de "descartado" persistente para este hito.
- **Sin polling nuevo**: se recalculan al abrir el panel y al cambiar de asociación objetivo, reutilizando la misma petición/infraestructura del panel; no se introduce un socket ni un sondeo periódico nuevo.
- **Resiliente a fallos parciales**: si una fuente de sugerencias falla, el resto de dominios y el resto del panel de Rubi siguen funcionando con normalidad; una sugerencia es una mejora, nunca una dependencia crítica.
- **No es UI intrusiva**: una sugerencia nunca abre el panel de Rubi automáticamente, nunca interrumpe al usuario con un popup; aparece dentro del panel solo cuando el usuario ya lo ha abierto.

## Provider

La API abstrae proveedores mediante `RubiProvider`/`RubiProviderFactory`. La selección se realiza por configuración de entorno y el provider predeterminado y actualmente seleccionado es Gemini, con modelo configurable. El uso real del provider tiene un kill switch independiente, límites, presupuestos persistentes, timeout y como máximo un retry seguro. No se documentan ni almacenan aquí secretos o API keys.

## Privacidad

El frontend envía solo mensaje, idioma, ruta, historial reciente saneable y contexto de pantalla allowlisted. La API elimina patrones de documento, email, teléfono, fecha y tokens antes del provider, abstrae del historial los datos de alta y nunca registra texto de conversación ni payloads de trámites. La observabilidad usa identificadores seudonimizados/truncados, categorías, estados, latencias, contadores y códigos seguros. El feedback del piloto es exclusivamente estructurado y no incluye conversación ni texto libre.

## Evolución

La infraestructura de piloto (acceso, feedback y telemetría) puede existir en el código sin constituir una apertura del producto: debe permanecer desactivada/no configurada hasta una autorización explícita.

Alta, modificación, baja, documentación, comunicación, actividades/calendario e inscripción son intenciones mutuamente excluyentes y se resuelven mediante una única clasificación (no una cascada de comprobaciones independientes en la que la primera evaluada "gana" por orden): se calculan los marcadores de tema, se descarta el que aparezca dentro de una negación explícita del usuario, y si queda más de un dominio activo se pide una aclaración concreta en lugar de adivinar. Ningún marcador de workflow puede basarse en palabras compartidas por varios trámites (persona, asociado, actividad, hacer, enviar o formulario); cada dominio exige una palabra o combinación propia. Cualquier workflow nuevo que añada su propio tema determinista debe integrarse en esta misma clasificación, no en una comprobación aparte evaluada antes o después de las demás.

Cada workflow nuevo debe demostrar y repetir el patrón ya validado:

`entender → recopilar de forma segura → preparar → revisión humana → confirmación → backend determinista`

Un workflow nuevo requiere revisar permisos, privacidad, contrato, idempotencia, concurrencia, telemetría y pruebas. No existe una cola automática de tareas y no debe introducirse implícitamente.

## Diagnóstico contextual de formularios (form-diagnostics)

Rubi puede conocer el estado funcional de un formulario mediante diagnóstico estructurado y sanitizado, pero nunca recibe los valores introducidos por el usuario.

- **Arquitectura**: `Angular Form → extractor genérico (form-diagnostics.util.ts) → RubiScreenContext.state.formDiagnostics → RubiConversationContext.validateScreenContext (allowlist cerrado) → RubiDeterministicRouter (intent `form_diagnostics`) → RubiFormDiagnostics.composeFormDiagnosticsMessage (plantillas ES/VA/EN)`. En ningún punto de esta cadena se lee `form.value`/`rawValue`; el extractor solo traduce el resultado ya calculado por los validadores de Angular (`control.errors`) a un código (`required`, `pattern`, `minItems`...) y, cuando existe, la etiqueta real del campo (metadata del formulario, nunca el DOM).
- **Contrato** (`RubiFormDiagnostics`/`RubiFormDiagnosticIssue` en `rubi-api.service.ts`): `{ present, valid, submitted?, issues: [{ field?, label?, code, source: 'client'|'server', required?, current? }] }`. `code` es siempre un identificador cerrado (allowlist en `RubiConversationContext.FORM_DIAGNOSTIC_ISSUE_CODES`, backend); un código no reconocido se rechaza (`RUBI_INVALID_SCREEN_CONTEXT`), nunca se reenvía como texto libre.
- **Nunca viaja**: valor del campo, NIF/teléfono/email/nombre reales, respuestas del formulario, adjuntos. Un error `pattern` (que en Angular incluye `actualValue` con el dato que falló) nunca copia ese campo; solo se conserva `code`/`field`/`label`.
- **Determinismo primero**: la respuesta a "¿qué me falta?"/"¿por qué no me deja enviar esto?" es una plantilla local (`RubiFormDiagnostics.js`) que traduce cada `code` a lenguaje natural; no requiere el provider y funciona igual con `RUBI_REAL_PROVIDER_ENABLED=false`. El provider nunca decide qué campo falla, si el formulario es válido o qué falta; como el resto de Rubi, solo podría (si estuviera habilitado) mejorar la redacción de hechos ya deterministas, y se ha optado deliberadamente por no exponer esta capacidad como tool seleccionable por el provider, precisamente para no añadir superficie de riesgo a una respuesta que ya es 100% determinista y gratuita.
- **UX de la pregunta**: solo se enumeran los `issues` cuando el usuario pregunta explícitamente (reconocimiento de intent tolerante a reformulaciones en ES/VA/EN, nunca una única frase exacta); Rubi no vuelca de forma espontánea una lista de campos pendientes solo porque el usuario acaba de abrir el formulario.
- **Formulario válido**: Rubi responde que no ve errores de validación pendientes; nunca afirma "todo está bien" (no tiene esa certeza, solo la ausencia de errores conocidos). Un botón deshabilitado por una condición de negocio conocida (participantes insuficientes, ejercicio no activo, inscripción fuera de plazo) se modela como un `issue` más (origen `client`, calculado a partir del mismo estado que ya bloquea el envío), así que queda cubierto por la misma respuesta sin lógica aparte.
- **Errores de backend**: solo códigos funcionales seguros ya existentes o explícitamente añadidos con este fin (`ALTA_CARGO_NO_DISPONIBLE`, `INSCRIPCION_PLAZO_CERRADO`, `ACTIVIDAD_NO_DISPONIBLE`...) se incorporan como `issue` con `source: 'server'`; nunca stack traces, SQL ni el mensaje interno completo.
- **Aislamiento**: el diagnóstico se recalcula en cada envío de mensaje (workflows Rubi) o en cada cambio relevante del formulario (Inscripciones, vía `RubiScreenContextService`); cambiar de inscripción, de workflow o cancelarlo nunca arrastra el diagnóstico anterior al siguiente turno.

## Decisiones permanentes de la estabilización post-auditoría (`fix/rubi-post-auditoria`)

- **Lectura de estado de inscripción, nunca confundida con iniciarla.** `check_inscripcion_estado` (capability `inscripciones.estado.read`) responde "¿estoy inscrito?"/"¿en qué actividades estoy inscrito?" (asociación) y "¿está esta asociación inscrita en X?" (Federación con target validado). Es estrictamente de solo lectura: nunca abre el formulario, nunca recoge datos, nunca devuelve participantes/respuestas/adjuntos. `inscripcion.start` sigue siendo la única vía para iniciar o editar una inscripción real, y no debe ampliarse para servir lecturas.
- **Cualquier endpoint REST que acepte un `asociacionId` de un actor no-asociación debe validar su existencia real en Censo**, no solo su tipo. `utils/associationExists.js` centraliza esa comprobación (ya usada en `controllers/Inscripciones.js`); un endpoint nuevo con ese patrón debe reutilizarla, no reinventar la validación.
- **El bloqueo de tools tiene dos capas, nunca una compitiendo con la otra.** `RUBI_BLOCKED_TOOLS` (infraestructura, variable de entorno) es siempre superior; el bloqueo administrativo persistente (`secretaria_rubi_admin_blocked_tools`, gestionado desde Configuración → RUBI) solo puede añadir restricciones, nunca levantar una ya impuesta por infraestructura. `effectiveBlockedTools` se calcula siempre como la unión de ambas listas en el único punto donde se aplican (`RubiGateway.message()`).
- **El catálogo de tools administrable se deriva del registro real (`RubiToolRegistry.allNames()`), nunca de una lista mantenida a mano** que pueda divergir silenciosamente de las tools que de verdad se pueden ejecutar.
- **La observabilidad agregada nunca guarda contenido conversacional ni PII**, ni siquiera para depurar un piloto: solo metadatos ya existentes o específicamente diseñados para ello (tool ejecutada, código de error, id de asociación, latencia). Si se necesita más detalle, se añaden columnas de metadatos, nunca texto libre.
- **PROVIDER y OPERACIÓN son dos conceptos de observabilidad distintos y nunca se mezclan en la misma cifra.** `secretaria_rubi_usage` mide exclusivamente el tramo que llega al proveedor de pago (tokens, coste, reservas de presupuesto); no representa el tráfico real de Rubi, porque las respuestas deterministas (la mayoría) nunca lo alimentan. `secretaria_rubi_telemetry` (vía `RubiPilotTelemetry`/`RubiTelemetryStore`) registra en cambio UNA fila por cada petición conversacional real (`conversation()`/`failure()` con `stage: 'conversation'`), determinista o vía provider, sin importar cuántos intentos/reintentos de provider haya habido dentro de esa misma petición — esos reintentos se cuentan aparte, solo en `secretaria_rubi_usage`, para no duplicar el conteo de "peticiones Rubi". Cualquier métrica nueva de "cuántas veces se usó Rubi" debe leer `secretaria_rubi_telemetry`, nunca `secretaria_rubi_usage`.
- **Un store de persistencia nuevo para Rubi nunca se conecta a base de datos por defecto.** Sigue el mismo patrón defensivo ya establecido (`RubiGateway`'s `adminService`/`usageStore`, `RubiPilotTelemetry`'s `store`): el factory correspondiente debe aceptar el store como opción con un no-op seguro por defecto, y el store real solo se conecta explícitamente en el único punto de producción que lo necesita (nunca como default de un factory que también usan tests u otras instanciaciones ad-hoc, que heredarían silenciosamente una conexión real).
- **Un valor de `asociacionId` no positivo (`<= 0`) recibido de un actor no-asociación nunca se trata como "manipulado".** Es el sentinel real que produce `AuthService.getIdAsociacion()`/`CensoService.asociacionId` para cualquier actor sin asociación propia, y varias pantallas de la aplicación (no solo Rubi) lo envían literalmente. Se trata siempre como equivalente a "no proporcionado" cuando el endpoint no exige un target real; solo un valor no numérico es sintácticamente inválido de verdad.
- **El contexto de pantalla lo alimentan las páginas reales, nunca el panel de Rubi por sí solo.** El panel solo añade el estado de sus propios workflows estructurados (alta/modificación/baja/documentación/comunicación en curso); toda otra señal de "dónde está el usuario y qué puede hacer" debe originarse en el componente de la página real vía `RubiScreenContextService`, con el contrato pequeño y explícito que ya valida `RubiConversationContext.validateScreenContext` (nunca campos libres ni PII).
- **Un workflow estructurado siempre tiene una salida visible.** Cualquier flujo nuevo de este tipo debe ofrecer, desde el primer momento, una forma evidente de cancelar y volver al chat sin depender de que el usuario encuentre el control interno del propio formulario.
